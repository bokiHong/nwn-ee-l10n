# 无冬之夜汉化工作台 · 渐进式重构方案

> 版本 v1 · 2026-10-07 深夜
> 前提：**不推翻重写**。现有的 `modl10n` 内核、`tm.sqlite` 里 43,942 条译文资产、产物安全网全部保留。
> 结论先行：**先补数据模型的"位置层"，再谈 GUI 合并。GUI 合并是结果，不是起点。**

## 一、先诊断：三个痛点是同一个根因

### 1.1 实测数据（全部现场查证，非估计）

| 项 | 实测值 |
|---|---|
| `scripts\modl10n\tm.sqlite` | 29,491,200 字节（29.5 MB） |
| `tm` 表总条数 | **43,942** 条（`auto` 41,063 / `manual` 2,879） |
| 来源 `src_mod` 分布 | PRC8 29,260 · Ch2 11,355 · Chapter One 3,325 |
| `mods` 表 | **只有 2 行**（Ch1 / Ch2） |
| 术语资产 | 散在 **4 个文件**（见 1.3） |
| 已安装 TLK | 11,995,940 字节；有文本槽位 30,168 = 英文 30,079 + 自加 89 |
| 自加槽位实测区间 | **90001~90089**（连续 89 条） |

### 1.2 根因：`tm` 表只有"译文↔原文"，没有"位置"

`tm` 表结构（`modl10n\tm.py:22-41`）：

```
tm(key TEXT PK, src, dst, src_mod, status, note, updated)
key = sha256(src)[:32]
```

一条译文**只记得第一次写入它的那个 mod**——因为写入用的是：

```sql
src_mod = COALESCE(tm.src_mod, excluded.src_mod)   -- tm.py:95，保留首次来源
```

证据链（三条，互相印证）：

1. `mods` 表只有 2 行，而 PRC8 的 29,260 条**完全没有位置记录**——因为它走的是 `tlk tool.py update` / `tlk.py import-txt` 这条路，那条路从不写 `mods` 表。**账本不全。**
2. `pipeline.process()` 里抽取出的 `units` 只活在内存（`pipeline.py:209-214`），跑完只剩一份 `report.json`，**位置信息随进程消失**。下次跑必须从零重抽取。
3. 自加槽位编号在**两处记录里互相矛盾**：`rebuild_tlk_safe.py:7` 注释写"实测 90001~90089"，而记忆库记录写的是"219901~219989"。现场实测证明 **90001~90089 才对**（30,168 − 30,079 = 89，且自加块全部落在 90xxx 区间）。**连一个刚做完的事实都记不住，说明没有账本。**

### 1.3 三个痛点 → 同一个根因

| 你说的痛点 | 真正的根因 | 现场证据 |
|---|---|---|
| **增量更新极痛苦** | 没有"位置层"，无法 diff。每次都要全量重抽取，回答不了"这次源文变没变" | `pipeline.py:209` 抽取结果不落库；`report.json` 是一次性快照 |
| **术语库无法实时检查 TLK 和 MOD** | 术语在 JSON、位置在内存、TLK 在二进制——**三者无法 JOIN** | `术语库编辑器.py` 是三个工具里**唯一完全不连 SQLite** 的（全靠 `subprocess` 调 `modl10n.rename` / `make_glossary.py`）；`tlk tool.py` 只有两处裸 SQL 读 `tm`（`:798-800`、`:832-833`）；`mod tool.py` 零裸 SQL |
| **TLK 的 ID 冲突无法在 MOD 中解决** | 没有 strref 分配账本 | `rebuild_tlk_safe.py:54-59` 只能用启发式反推自加槽位：**"英文导出 `prc8.txt` 里没有的、且有文本的"**——一旦某自加槽位与英文导出重合、或英文导出某条是空文本，就会误判 |

**所以重构顺序必须是：数据库先行 → 服务层 → GUI 合并。**

## 二、红线：要保住的三样东西

1. **`tm` 表的 key 空间**：`key = sha256(…)`。43,942 条资产**原地不动，一列不改**。

   **⚠ Sprint 1 全量核验后的修正**（2026-10-08 实测，推翻本节原先"两条流程已共用同一 key 空间"的说法）：

   ```
   43,942 = 孤儿 64 + 未规范 src 117 + 已规范 43,761
   ```

   | 类别 | 条数 | 事实 | 后果 |
   |---|---|---|---|
   | 已规范 | 43,761 | `sha256(src)` 与 `sha256(norm(src))` 相同 | 两条流程都能命中 ✓ |
   | **未规范 src** | **117**（前导空白 15 / 尾随空白 102） | key 是按 **raw** 算的；按 norm 命中 **0 条** | TLK 流程（先 norm）**算不出同一 key** → 同一句英文被当成新条目**重译** ✗ |
   | **孤儿** | **64**（`src=''`，全部来自 Chapter One） | 旧 `sf_cache.json` 导入时 `src_lookup` 缺原文字符串（`tm.py:156-166` 的已知行为） | 译文在库里，但**永远无法按内容命中** ✗ |

   所以"共用同一 key 空间"**只对 99.6%（43,761/43,942）的条目成立**。这正是需要 `l10n\keys.py` 把 key 计算收成一处的原因；Sprint 3 的 `diff` 必须显式处理这 181 条，不能假装它们不存在。

   **Sprint 2 实战验证（Ch1 原始英文模组，2026-10-08 实测）**：

   | 项 | 实测 |
   |---|---|
   | 单元总数 | 5,731（与 `mods` 表记录的 `units=5731` **完全一致**） |
   | 去重后不同文本 | 3,325（与 `tm` 里 Chapter One 的 3,325 条、`mods.reused=3325` **三方吻合**） |
   | 用 `norm` key 查库命中 | 3,274（98.5%） |
   | 未命中 | **51 条 —— 全部能用 `raw` key 命中** ✓ |

   **结论：这 51 条不是"没译文"，而是"两种 key 算法没对齐"。**
   → **Sprint 3 的查库必须两个 key 都试（兜底）**，不能只用一种。这是本次重构最有价值的一条实测结论。
2. **`modl10n\core\`**：`erf.py` / `gff.py` / `sfrules.py` / `classify.py` 是逐字节验证过的地基，不动。
3. **产物安全网**：原子写（`.tmp-writing` → `os.replace`）、只读位清理（WinError 5）、`--inplace` 自动备份 + 大小校验、读回校验、`.ncs` 字符串常量**硬校验**。新架构只许**调用**，不许绕过。

## 三、统一数据模型

### 3.1 分层（三层 + 两个横切资产）

```
容器层 Container     .mod / .tlk / .hak —— 一个物理文件
   │ 1:N
资源层 Resource      resref + ext（prc_nui_sb_view.ncs、asabicave001.git）
   │ 1:N
单元层 StringUnit    "一次可译出现"（GFF 字段 / nss 字面量 / TLK strref）
   ▲ N:1（按内容哈希）
资产层 TMEntry       译文（key = sha256(norm(src))）—— 跨项目复用的唯一真源
资产层 Term          术语：译名 + 分类 + 必守等级 + 生命状态
```

### 3.2 ★ 最重要的一条不变量

> **译文只存在 `TMEntry`。`StringUnit` 只存"位置"和"源文哈希"，不存译文副本。**

理由：这就是现有架构已经在做的事实——`mod tool.py` 的顶部注释写着"译文只存在 `modl10n\tm.sqlite` 里，打包时脚本是从记忆库取译文的"，而 `review` 子命令的核心原理也是"只改导出的 txt 不生效，必须回导记忆库"。

**沿用这个不变量，43,942 条资产零迁移；反过来把译文复制进 `unit` 表，立刻产生双写不一致。**

### 3.3 `StringUnit` 类设计

```python
# l10n/model.py
from dataclasses import dataclass

@dataclass
class StringUnit:
    """一条"可译出现"。注意：它不持有译文，只持有源文的哈希。"""

    # ---- 身份
    uid: str            # 稳定主键：sha1(f"{container_id}|{resref}|{kind}|{locator}")[:16]
    project: str        # 归属：swordflight / prc8 / 全局
    container_id: int   # -> container.id

    # ---- 位置（资源维度）
    resref: str         # "prc_nui_sb_view"（不含扩展名，统一小写）
    ext: str            # "ncs" / "nss" / "dlg" / "ifo" / "tlk"
    kind: str           # gff | nss | tlk —— 决定用哪个回写器
    field_path: str     # 给人看的定位："ifo:Mod_Description" / "nss:1240#2" / "tlk:90001"
    locator: str        # 给机器用的定位（JSON）：["gff",12,3] / ["nss",12,1240,2] / ["tlk",90001]

    # ---- 内容
    src_text: str       # 英文原文（GFF 已按现有约定 escape：真实换行 -> 两字符 \n）
    src_key: str        # = key_of(norm(src_text))  -> 指向 tm.key
    src_hash_seen: str  # 上次扫描时 src_text 的哈希 —— 用来判断"源文变没变"
    context: str        # 上下文（同资源相邻文本），给人工译者和 AI 看

    # ---- 分析结果（缓存，可重算）
    placeholders: str   # JSON：["<CUSTOM0>", "%(NAME)", "1d6", "\n\n"]
    term_hits: str      # JSON：[["Swordsage","贤者之剑",true], ...]

    # ---- 状态机
    storage: str        # inline（写回 GFF 内嵌）| tlk_strref（改道到自定义 TLK）| tlk_slot（TLK 本体条目）
    status: str         # new | kept | src_changed | gone | skipped | ignored
    first_seen: str
    last_seen: str
```

**三个设计要点：**

1. **`kind` 决定回写器**：`gff` → `modl10n\core\gff.py`；`nss` → `core\classify.py` + `ncs.py` 重编译；`tlk` → `modl10n\tlk.py:write_tlk()`。
2. **`field_path` 与 `locator` 分工明确**：`field_path` 给人看（GUI 表格列、报告），`locator` 给机器回写用。
   - 现有 `extract.Unit.locator` 是 tuple（`extract.py:32-52`），落库序列化成 JSON 即可——**`apply_units()` 的签名不用改**（它收的是 `{locator: 译文}` 的 dict）。
3. **`storage` 是新增维度**，吸收 `tlkroute.py` 那次"内嵌 GFF → 模块自定义 TLK + strref"的改道实验。

### 3.4 `Resource` 类设计

```python
@dataclass
class Resource:
    rid: str            # sha1(f"{container_id}|{resref}.{ext}")[:16]
    container_id: int
    resref: str
    ext: str
    size: int
    sha256: str         # 资源字节哈希 —— 判断"这次要不要重新抽取"
    gff_type: str       # "IFO " / "DLG "（仅 GFF 有）
    deps: str           # JSON：引用的其它 resref（.nss 里的调用、.git 里的 area tag）
    units_total: int    # 该资源里的单元数（缓存，用于筛选"哪些资源还有英文"）
    units_done: int     # 已有译文的单元数
    change_state: str   # unchanged | modified | added | removed
    first_seen: str
    last_seen: str
```

### 3.5 `TlkSlot` —— 专治"ID 冲突"

```python
@dataclass
class TlkSlot:
    tlk_path: str       # 哪个 TLK（prc8_consortium.tlk / 模块自定义 TLK）
    strref: int         # 槽位号
    owner: str          # 谁占的：prc8 / swordflight-ch1 / 工作台
    purpose: str        # engine_text（中文界面标签）| routed（内嵌改道追加）| reserved
    text_key: str       # 内容的哈希（-> tm.key），槽位内容随时可重建
    protected: bool     # True = 重建时绝不能清（取代 rebuild_tlk_safe 的启发式）
    note: str
```

**这一张表直接消灭三件事：**

1. `rebuild_tlk_safe.py` 的启发式 → 换成 `SELECT strref FROM tlk_slot WHERE tlk_path=? AND protected=1`，**绝对可靠**。
2. 编号记错（90001~90089 vs 219901~219989 已在记录里矛盾）→ 一次"认领"后落库，成为唯一事实。
3. 多 mod 抢槽位 → 分配器 `allocate(tlk_path, owner, text, purpose)` 先查占用再写，冲突时**抛错而不是静默覆盖**。

## 四、SQLite 中央存储

### 4.1 决策：升级现有 `tm.sqlite`，不新建库

| 方案 | 判断 |
|---|---|
| A. 新建 `l10n.db`，从 tm 迁移 | ✗ 要搬 43,942 条资产 + 改写全部 key 逻辑，风险大、无收益 |
| **B. 原地升级 `tm.sqlite`（加表）** | ✓ **采用**。`tm`/`mods` 一字不改，现有 7 个 CLI 与 3 个 GUI 全部继续能跑 |

- 用 `PRAGMA user_version` 做版本号；`l10n/db.py` 里写**幂等**迁移，旧库首次打开自动升级（只 `CREATE TABLE` + 回填数据，**不 ALTER `tm`**）。
- **文件名保持 `tm.sqlite`**。它被写死在 `tlk tool.py:463`、`mod tool.py:40`、`rebuild_tlk_safe.py:76` 等至少 10 处；改名收益远小于风险。
- 对外称"**中央库**"，路径仍是 `scripts\modl10n\tm.sqlite`。

**两个视图（GUI 直接拿来当数据源）：**

```sql
-- (1) 某项目"待办清单"：哪些单元还没译文 / 源文变了
CREATE VIEW IF NOT EXISTS v_unit_todo AS
SELECT u.uid, u.project, u.container_id, u.resref, u.ext, u.field_path,
       u.src_text, t.dst AS dst, u.status, u.storage,
       u.term_hits, u.placeholders,
       (t.key IS NOT NULL) AS has_dst
FROM unit u
LEFT JOIN tm t ON t.key = u.src_key AND t.status != 'rejected';

-- (2) ★ 术语违规全库检查：原文命中【必守】术语、但译文没用规范译名
--     这一条 SQL 就是"术语库实时检查 TLK 和 MOD"的答案
CREATE VIEW IF NOT EXISTS v_term_violation AS
SELECT u.project, u.resref, u.ext, u.field_path, ut.en, ut.zh,
       (ut.zh IS NOT NULL) AS required_hit, t.dst
FROM unit u
JOIN unit_term ut ON ut.uid = u.uid AND ut.required = 1
LEFT JOIN tm t ON t.key = u.src_key
WHERE t.dst IS NOT NULL AND instr(t.dst, ut.zh) = 0;
```

> 注意 `v_term_violation` 把 TLK 与 `.mod` 的单元**放在同一张 `unit` 表里**，所以它们的术语违规能被同一条 SQL 查出来——这正是现有架构做不到的（术语在 JSON、位置在内存、TLK 在二进制）。

### 10.1 一个必须记录的解码坑（PRC8 那 22 条的根因）

那 22 条待译**全部**含 U+FFFD 替换符（全库只有 37 个单元含它）。根因是一条**双重损坏**的链条：

1. PRC8 的 TLK 是**官方 CP-1252 编码**的英文，其中的智能引号 `"` 是单字节 `0x93`/`0x94`；
2. `modl10n.tlk.load_texts` 用 `decode("utf-8", "replace")` → `0x93/0x94` 变成 **U+FFFD**；
3. 而 `tm` 里对应那批文本，历史上是用**另一种错误解码（GBK 风格）**导入的 —— `"` 变成 `?`，**并且吞掉了后面的空格**（GBK 把 `0x94`+空格当成一个双字节字符）；
4. 两边损坏方式不同 → key 不同 → 被判定成"待译"。

精确证据（`tlk:13104`，2,035 字长的怪物描述，**第一处差异在第 771 字符**）：

```
TLK 侧 : ...as �mongrels,� not because...     ← U+FFFD，空格还在
tm  侧 : ...as �mongrels,?not because...      ← '?'，空格被吞
原文应为: ...as "mongrels," not because...    ← CP-1252 智能引号
```

**处置建议（不违反"`tm` 不动"红线）**：

- **短期：不动。** 22 条重译只要 ￥0.19，收益远小于改动 43,942 条资产的风险。
- **中长期**：单列一个"编码修正"任务 —— 用 CP1252 重新解码这批（`tm` 里 33 条含 U+FFFD + 22 条待译），修正 `src` 与 `key`。**必须单独拍板**，因为它会改 `tm`。
- **代码侧**：`extract_tlk` 的解码方式应做成可配置参数；**默认保持 utf-8 replace**，因为这是在"`tm` 不动"前提下命中率最优的选择（改 CP1252 反而会让 15 条原本能命中的变成待译）。
